# 输出契约：kb-query 回答

## 结构

```
一句话结论（最可能的方向 + 第一个该做的动作）

**症状确认**
- 现象（来源 ID）

**可能原因（按排查成本排序）**
1. 原因名（cause_ref ID，可信度）
   判别依据：<discriminator 内容>
2. ...

**排查路径**
1. 第一步：能一次排除大片可能性的检查
2. ...

**处置动作**
- 动作（action_ref ID）

**影响范围**
- 沿 blocks / may_cause 展开

**溯源**
kb 实例：kb.xx.yyy
本体节点：core.anomaly.xxx, ap.process.yyy
未覆盖部分：<明确说明哪些是本体外的推断>
```

## 硬要求

- 每条结论后括号标 ID。用户要能自己核对，也要能在结论错时知道改哪个文件。
- `confidence` 为 `low` 的内容明确标注，不要说成定论。
- 本体未覆盖的推断单独分节，不与已沉淀知识混排。
- 排查路径的排序按**排查效率**（先做便宜的排除性检查），不按 `likelihood` 高低。
- 不假装有实时工厂数据。回答的是"可能原因与排查路径"，不是"你厂现在是哪个原因"。

## 长度

简单问题直接答，不要套满全部小节。
只有涉及多根因排查的问题才需要完整结构。
